### **Контекстная и контейнерная диаграммы**

Представлены контекстная диаграмма и контейнерная диаграмма на уровне одного кластера Kubernetes.

Дата-центры будем распределять географически, каждый дата-центр — отдельный кластер Kubernetes. Представляется, что такое деление упрощает организацию инфраструктуры, позволяет легко масштабироваться (добавлять новые дата-центры), при этом позволяет построить необходимую архитектуру.

GSLB обеспечивает выбор необходимого пользователю дата-центра (по географической доступности и по доступности вообще по health check), и пользователь использует выбранный дата-центр на протяжении всей сессии.

### **Состав кластера**

Каждый кластер содержит сервисы:
* **core-app** — для оформления страховок
* **client-info** — для поддержания базы клиентов и получения данных клиентов

Информация об оформленных страховках и клиентах публикуется в сервис **Kafka** как события с помощью сервиса **Debezium** (вычитывает из БД, обеспечивает атомарность операции). Информация о клиентах реплицируется на Kafka других кластеров с помощью **MirrorMaker** в двунаправленном режиме (нет мастера).

---

Каждый кластер содержит сервисы:
* **ins-product-aggregator**
* **ins-comp-settlement**

Только один кластер содержит эти сервисы активными, другие — только в **standby** режиме. Выбор кластера с активными сервисами происходит с помощью **Kubernetes Lease** путём блокировки файла в облачном хранилище **S3** (любой облачный сервис, например Yandex).

Активные сервисы взаимодействуют с внешними сервисами, * **ins-product-aggregator** пишет в Kafka, информация в Kafka реплицируется на Kafka других кластеров с помощью **MirrorMaker** в двунаправленном режиме. Кластер с активными сервисами таким образом автоматически становится мастером.

---

### **Стратегии масштабирования**

* **Для сервисов `core-app`, `client-info`** применим **автоматическое горизонтальное масштабирование**, используя метрики загрузки по памяти и по числу запросов.
* **Для сервисов `ins-product-aggregator`, `ins-comp-settlement`** будем использовать **ручное горизонтальное масштабирование** — конфигурирование инстанса сервиса для работы с отдельной страховой компанией-партнёром. Также будем использовать **автоматическое вертикальное масштабирование**, используя метрики загрузки по памяти и CPU.

Шардирование БД на данном этапе использовать не будем. Лучше посмотреть в сторону оптимизации хранения информации (избавимся от избыточных данных) и оптимизации их извлечения.
